# 실측 — RTF 병목은 렌더링이 아니라 모델 엔티티 수다

**측정일**: 2026-07-25 · **환경**: gz-sim 8.11.0, GTX 1660 SUPER, 헤드리스(`-s -r`)
**재현**: `bash scripts/bench_rtf.sh <world.sdf> <라벨>`

"디테일을 더 넣으면 시뮬레이션에 무리인가?"에 답하기 위해 요소별로 분리 측정했다.

## 측정

| # | 구성 | 모델 엔티티 | RTF |
|---|---|---:|---:|
| A | 과수원만, 센서 0, FCL 충돌 | 1,754 | 0.274 |
| B | A + bullet 충돌검출 | 1,754 | 0.304 |
| C | **과실 인스턴스 제거** | 554 | **1.211** |
| D | 디테일 최대 + 로봇/센서, 과실 0 | 443 | 0.718 |
| E | 디테일 최대 + 로봇/센서 + 과실 1,200 | 1,643 | 0.230 |

## 결론

**1. 병목은 렌더링이 아니다.** A는 센서가 하나도 없는 헤드리스 실행인데 이미 0.274다.
로봇과 카메라 3대를 얹어도 크게 나빠지지 않았다(0.30). 렌더링은 범인이 아니었다.

**2. 비용은 삼각형 수가 아니라 모델 엔티티 개수에 붙는다.** C가 결정적이다 —
과실 인스턴스 1,200개를 빼자 1,754→554 엔티티에서 RTF가 **4배**(0.30→1.21) 뛰었다.
삼각형은 과실이 80 tris 짜리라 거의 줄지 않았는데도 그렇다.

**3. 그러므로 디테일은 "모델을 많이"가 아니라 "한 모델 안에 visual 을 많이" 로 넣는다.**
이 원칙으로 환경·행 디테일을 재구성한 결과:

| | 이전 | 이후 |
|---|---:|---:|
| 환경 모델 엔티티 | 76 | **14** |
| 행 디테일 모델 엔티티 | 80 (지주만) | **30** |
| visual 총계 | ~700 | **2,488** |

디테일은 3배 이상 늘리면서 엔티티는 절반 이하로 줄였다. `Prop` 클래스가 이 규율을 강제한다.

**4. bullet 충돌검출은 효과가 작았다(+0.03).** 설계서 §4.2 권고대로 켜두되,
하이트맵 충돌이 주범이라는 가설은 기각한다.

## 운영 방침 — 월드 2종으로 분리

과실별 인스턴스는 **정답 라벨 생성에만** 필요하다(2026-07-25 라벨 실측 참조).
주행·SLAM 개발에는 불필요하므로 월드를 나눈다.

| 월드 | 용도 | 과실 인스턴스 | RTF |
|---|---|---:|---:|
| `orchard_nav.sdf` | Nav2·FAST-LIO2 개발, 실시간 주행 | 0 | **0.72** |
| `orchard_gt.sdf` | 데이터셋 생성 (`real_time_factor=0` 으로 최대속도 실행) | 1,200 | 0.23 |

데이터셋 생성은 실시간일 필요가 없으므로 0.23이 문제되지 않는다.

## 남은 레버 (아직 미적용)

- **Levels** (`--levels`): 로봇 주변 열만 상주. 400그루 → ~100그루 상주로 줄일 수 있다
- 수관 카메라 1920×1080 상시 → 촬영 시점만 켜기
- `SceneBroadcaster` 발행 주기 조절
